3 ОПИС ВИКОНАНОЇ РОБОТИ

3.1 Загальні відомості про систему 

Назва системи: Spotify.
Розробник: Spotify AB (Швеція), публічна компанія (з 2018 року). 
Призначення системи: Глобальна платформа потокового аудіо (музика, подкасти, аудіокниги, live-події). 
Користувачі: понад 600 млн щомісячних активних користувачів (MAU) у 190+ країнах (станом на 2025–2026), меломани, поціновувачі музики. 
Основні функції: персоналізоване відтворення та рекомендації, створення та спільний доступ до плейлистів, офлайн-режим, аналітика прослуховувань у реальному часі (мільярди подій на день, соціальні елементи та монетизація для артистів. 

3.2	Архітектурний стиль системи 

Архітектурний стиль — мікросервісна подієво-орієнтована (event-driven) система з акцентом на децентралізацію та хмарно-нативний підхід. Архітектура тісно пов'язана з моделлю управління командами (Squad, Tribe, Chapter, Guild), де кожна автономна команда розробників (Squad) відповідає за повний життєвий цикл свого сервісу від UI до бази даних. Основні функції (пошук, плейлисти, рекомендації) реалізовано як незалежні модулі, що дозволяє швидко виявляти помилки без блокування всієї системи та оперативно проводити A/B тестування.

3.3	 Основні компоненти системи

Інтерфейс користувача реалізовано за допомогою бібліотек React (веб), React Native/Swift/Kotlin (мобільні), Electron (десктоп). 
Серверна частина реалізована як мікросервіси на Java/Spring Boot (основна), Scala, Node.js, Go. Тобто, на рівні бізнес-логіки є окремі сервіси (Playback, Recommendation Engine, Search, User Profile, Analytics, тощо), які працюють над своїми вузько-спеціалізованими задачами та можуть масштабуватися незалежно.
На рівні зберігання даних використовюється Cassandra (плейлисти, користувацькі дані), Redis (кеш метаданих), PostgreSQL (транзакції), BigQuery + Google Cloud Storage (аналітика та аудіо-файли).
Допоміжні сервіси: Apache Kafka (основний event bus), Google Pub/Sub (фонова обробка), Kubernetes + Docker (оркестрація), Backstage (внутрішній developer portal для управління мікросервісами), Prometheus + Grafana (моніторинг), Terraform (IaC).

3.4	 Взаємодія компонентів 

Внутрішня комунікація базується на gRPC та REST API. Для відтворення музики застосовуються HTTP range-запити (завантаження аудіо у форматах OGG Vorbis або AAC частинами) та локальна буферизація. Клієнти підключаються до найближчого дата-центру через API Gateway, який відповідає за балансування, автентифікацію (OAuth 2.0) та rate-limiting. Обробка мільярдів подій у реальному часі працює через Apache Kafka (потік подій), Apache Storm та Google Pub/Sub (публікація-підписка).

3.6	 Приклади програмної реалізації 

У межах дослідження було розглянуто спрощену модель подієво-орієнтованої мікросервісної архітектури, подібної до тієї, що використовується у стримінгових платформах (наприклад, Spotify). Основною ідеєю є асинхронна взаємодія сервісів через брокер повідомлень Apache Kafka.
1. Сервіс генерації подій (Producer)
Сервіс відтворення музики формує події (PlaybackEvent) та публікує їх у Kafka-топік. Ключем повідомлення виступає ідентифікатор користувача, що забезпечує впорядкованість подій у межах одного користувача. Конфігурація Kafka-продюсера визначає параметри надійності доставки. Код наведено у додатку В.
Використання параметра enable.idempotence=true дозволяє уникнути дублювання повідомлень при повторних спробах відправки.
У реальних системах використовується декілька топіків для різних етапів обробки даних.
Такий підхід дозволяє:
•	виконувати повторну обробку даних; 
•	ізолювати різні етапи обробки; 
•	масштабувати систему незалежно по компонентах. 
2. Сервіс обробки подій (Consumer)
Аналітичні або інші сервіси підписуються на Kafka-топіки та обробляють події асинхронно.
Для забезпечення контролю над доставкою використовується ручне підтвердження обробки повідомлень (manual commit).
3. Потокова обробка даних (Stream Processing)
Для агрегації великих обсягів даних застосовуються потокові фреймворки (наприклад, Apache Beam / Scio). Обробка включає фільтрацію, групування та агрегацію подій. Код наведено у додатку В.
Використання вікон (windowing) дозволяє агрегувати дані за певні інтервали часу (наприклад, доба).
4. Обробка помилок (Dead Letter Queue)
Для підвищення надійності системи застосовується шаблон DLQ (Dead Letter Queue). Повідомлення, які не вдалося обробити, перенаправляються в окремий топік.

1 private void handleFailure(ConsumerRecord<String, PlaybackEvent> record, Exception ex) {
2    kafkaTemplate.send("playback-events-dlq", record.key(), record.value());
3 }

Це дозволяє уникнути блокування основного потоку обробки.
5. Додаткові споживачі подій
Kafka дозволяє підключати декілька незалежних споживачів до одного топіку. Наприклад, сервіс рекомендацій:

1 @KafkaListener(topics = "playback-events", groupId = "recommendation-service")
2 public void handle(PlaybackEvent event) {
3    updateUserEmbedding(event);
4    updateRecommendations(event.getUserId());
5 }

Таким чином, одна подія використовується одночасно різними підсистемами без прямої залежності між ними.
6. Особливості забезпечення надійності
У подібних системах зазвичай використовується модель доставки at-least-once. Це означає, що повідомлення може бути доставлено більше одного разу, тому необхідна ідентифікація подій.
Приклад дедуплікації:

1 .distinctBy(_.eventId)

Основні аспекти:
•	унікальний ідентифікатор події (eventId); 
•	обробка дублікатів на рівні споживача; 
•	збереження порядку подій через ключ (userId). 
8. Узагальнена схема роботи
Загальний процес функціонування системи:
1.	Сервіс відтворення генерує подію. 
2.	Подія публікується у Kafka. 
3.	Kafka забезпечує збереження та доставку повідомлень. 
4.	Подію обробляють декілька сервісів: 
o	аналітика; 
o	рекомендації; 
o	моніторинг. 
5.	Результати зберігаються у відповідних сховищах (аналітичні бази, кеші, ML-системи).

2. The Step-by-Step Execution Flow

Phase 1: The Request and Security Handshake

Step	Source	Target	Description
1	User	Client App	Clicks "Play" on Track X.
2	Client App	API Gateway	Sends POST /v1/me/player/play containing the Track_ID. Header includes Authorization: Bearer <JWT>.
3	API Gateway	Auth Service	Forwards JWT for validation and scopes check.
4	Auth Service	API Gateway	Returns 200 OK (Token is valid, user ID extracted).
Phase 2: Authorization and Token Generation

Step	Source	Target	Description
5	API Gateway	Streaming Service	Routes the validated request, passing along the User ID and Track_ID.
6	Streaming Service	Entitlement Service	Requests a check via internal gRPC: "Is this user allowed to play this track?" (Checks Premium status, Geofencing, and label licensing restrictions).
7	Entitlement Service	Streaming Service	Returns True.
8	Streaming Service	Streaming Service (Self-Message)	Generates a short-lived, cryptographically signed URL pointing to the requested audio file on the CDN. It also fetches the DRM decryption key.
9	Streaming Service	API Gateway	Returns the signed CDN URL and DRM key.
10	API Gateway	Client App	Returns 200 OK with the CDN URL and DRM key payload.
Phase 3: The Data Plane (Audio Streaming)

Step	Source	Target	Description
11	Client App	CDN Edge Node	Initiates a direct GET request to the signed URL for the first chunk of the audio file (e.g., Range: bytes=0-500000).
12	CDN Edge Node	Client App	Streams back the encrypted audio bytes.
13	Client App	Client App (Self-Message)	Decrypts the chunks into the local buffer and begins audio playback.
14	Client App	User	Audio plays.
Phase 4: Asynchronous Telemetry
(This happens parallel to playback, usually triggered after 30 seconds of listening to count as a "stream")

Step	Source	Target	Description
15	Client App	API Gateway	Sends an async telemetry payload: POST /v1/events/playback (Contains timestamp, Track_ID, duration listened).
16	API Gateway	Telemetry Ingestion (Kafka)	Publishes the event to a Kafka topic (playback_events) as a fire-and-forget message.
Important Note: Do not expect a synchronous response back to the client from Kafka; the API Gateway just acknowledges receipt (202 Accepted).
